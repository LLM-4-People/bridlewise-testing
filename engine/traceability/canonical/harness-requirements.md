# Code Harness Requirements Ledger

Status: working source of truth for the current design investigation. Repository implementation remains paused until the OpenCode evidence review, code-intelligence benchmark, and all explicit pending user decisions in this ledger are complete. Every normative requirement has a stable `REQ-*` source-intent ID in the traceability table; section bullets refine those requirements and cannot silently weaken them.

## Product boundary

- Provider- and LLM-agnostic core. The existing AI SDK/OpenAI-compatible integration is the first adapter, not a core architectural dependency.
- No orchestration, policy, subagent, MCP, research, audit, rollback, checkpoint, interaction, or storage module may depend on Makora, GLM, or an OpenAI-specific wire shape.
- Provider adapters normalize messages, tool calls/results, streaming, structured output, context/output limits, usage/cache/reasoning tokens, cost, finish reasons, retries/rate limits, headers/metadata when exposed, and typed errors.
- Select providers/models and role-specific overrides from central config. Discover and validate capabilities at startup/run time; unsupported required capabilities must produce a clear capability error or user decision, never silent emulation.
- Add adapter conformance tests and provider-neutral fixtures so another provider/model can be added without rewriting core workflow logic.
- Treat every LLM as fallible, forgetful, non-autonomous, and untrusted for control decisions. The LLM proposes plans/actions/interpretations; deterministic harness code and explicit human approvals own authority.
- The model cannot directly mutate authoritative state, bypass/disable gates, grant permissions, approve its own high-risk action, suppress diagnostics, mark required evidence complete, promote code, or rewrite audit history.
- No Codex App Server, Codex-specific configuration, Codex hooks, or Codex-specific agent machinery in the harness.
- Command-line interaction first; preserve a transport-neutral application boundary so a web interface can be added later without duplicating workflow logic.
- Interactive multi-turn operation, including steering/addenda while work is active and explicit clarification whenever a decision or intent is unclear.
- Reject Codex-specific packages, endpoints, hooks, config keys, state, and wire assumptions with architecture/dependency tests; negative documentation of the product boundary is not a runtime dependency.
- Carry authenticated principal, project, workspace, and authorization scope through the transport-neutral service contract from the first CLI release so a later web interface cannot bypass or bolt authorization onto globally keyed state.

## Engineering policy

- Apply DRY, KISS, YAGNI, correctness, security, maintainability, and current best practice.
- Build as small composable blocks/modules with shared reusable functions and logic.
- Keep exactly one user-editable central harness configuration document, validated by one typed versioned schema, as the source of truth for every configurable parameter and policy toggle. Secrets are opaque references to an external secret store, environment provider, or protected key file, never literal config values.
- Before creating anything, search the entire current codebase for reusable or adaptable modules, symbols, schemas, workflows, and tests. Return concrete reuse candidates with file/symbol evidence.
- Before adding or duplicating any module, function, method, type, constant, configuration key, schema, migration, command, adapter, workflow, UI component, test helper, fixture, or policy, search the entire current repository and dependency/extension map for a reusable or adaptable candidate and return file/symbol evidence.
- Refactor and clean the complete accepted feature touch set and its directly affected dependency cone; remove superseded code, dead paths, obsolete tests/configuration, and duplication. Work outside that evidence-backed scope requires a new declared change set and user decision, preventing both incomplete cleanup and unrelated rewrites.
- Never use band-aids or silent workarounds. Diagnose and correct root causes.
- Never over-engineer. Add only mechanisms justified by a current requirement or measured failure.
- Select and update to the latest non-prerelease, non-yanked, security-acceptable stable dependency/tool release from authoritative publisher metadata. Record the exact resolved version/artifact digest in the lock/evidence record so a run is reproducible; that reproducibility lock is not a deliberate old-version constraint.
- A manifest/runtime/toolchain constraint that prevents selecting latest stable is allowed only for demonstrated compatibility or security evidence and must record owner, reason, evidence, affected scope, creation and review/expiry dates, latest-stable comparison, automated update check, and upgrade/removal path. An unregistered or expired constraint blocks completion.
- Research current stacks, APIs, and external/version-sensitive facts from primary sources. Never fabricate missing evidence.
- Every finding or claim used for design, implementation, diagnosis, ranking, completion, or user guidance must be verified by at least three independent evidence sources or methods and reproduced against the applicable environment whenever reproduction is logically or physically possible. Three pages repeating one upstream claim count as one source.
- If triple verification or reproduction cannot be completed, record the exact unavailable check and reason, mark the finding `unknown` rather than true/false, block dependent work, and ask the user how to proceed. The model cannot decide that verification is unnecessary or silently convert an unknown into an assumption.
- Ask the user whenever any requirement, intent, safe default, scope, behavior, storage, security, cost, external side effect, configuration, or architecture choice is unclear. Until answered, represent the ambiguity as a typed unresolved decision and block any action whose result could differ between plausible interpretations.
- Define “best coding principles” with a versioned review rubric covering correctness, security, maintainability, simplicity, cohesion/coupling, duplication, testability, observability, performance proportionality, accessibility where applicable, and current ecosystem practice. Completion requires deterministic checks where possible plus independent review evidence for judgment-only criteria.
- Every change plan records its complexity and abstraction delta, reuse decision, deleted/superseded surface, and why each new mechanism is required. Risk tiers may add proportionate tests/review but cannot remove the mandatory research, reuse, verification, audit, mutation-safety, or quality floors.

## Canonical configuration and authority model

- The harness exposes exactly one user-editable central configuration document at a well-known or explicitly supplied path. Modular code may own typed schema fragments, but build-time composition produces one canonical schema and one validated document; hidden secondary config files, duplicated defaults, model prompt constants, environment-specific literals, and per-module policy stores are forbidden.
- Existing repository compiler/linter/test/package configuration remains authoritative input for that external project and is never copied into a second harness policy store. The central harness document alone configures how such project files are discovered, validated, respected, and overridden through an explicit user decision.
- Classify every static value as one of: configurable parameter in the central document; secret handle resolved outside it; derived value computed from declared inputs; test/fixture value confined to tests; protocol/persistence constant tied to an external specification; or stable non-configurable domain/root-of-trust invariant with a requirement ID and rationale. Architecture/static tests reject unclassified or duplicated operational constants.
- The central schema defines schema version, defaults, precedence, unknown-key rejection, deprecations/migrations, mutability class, secret classification, owner module, validation, documentation, and test linkage for every key. Generated CLI/reference documentation comes from this schema.
- The schema has typed groups for core/project/profile loading; provider/model adapters and budgets; agents/routing/leases; MCP/research/currentness/verification; dependency resolution and constraint exceptions; repository identity/index/manifests; editor/mutation; quality packs/gates; feature/checkpoint/promotion; memory/coordination; attempts/retries; retrieval; audit/evidence/retention; security/sandbox/egress/roles; rollback; self-evolution; evaluation matrices/thresholds; and interaction/approval behavior. Adding another parameter anywhere requires adding it to this one schema and generated document first.
- A validated configuration snapshot is deeply immutable for its lifetime. Hot reload never mutates it: it validates a complete replacement, creates a content-hashed new version, records an append-only intent/diff/approval/result event, atomically switches at a declared safe boundary, and either migrates an active run through a checkpoint or leaves that run pinned to its original snapshot. Failed reload restores the previous version.
- Root-of-trust invariants, audit integrity, authorization ceilings, secret isolation, mutation mediation, and required evidence/gate floors are not configuration toggles and cannot be weakened by config, environment, CLI flags, provider output, plugins, MCP, agents, or project files.
- Authority is single-source per fact and ordered by domain: the immutable root-of-trust policy defines non-overridable safety; an authenticated user decision authorizes only a scoped action inside that policy; the versioned central config snapshot defines configurable policy; the append-only journal defines lifecycle/coordination/approval state; Git plus authoritative filesystem hashes define source bytes; the encrypted evidence vault defines retained full-fidelity payload bytes; and indexes, caches, summaries, dashboards, prompts, and CLI/web views are rebuildable projections only.
- Every cross-domain reference carries config version, journal cursor/event ID, repository/base/checkpoint hash, evidence hash, actor, and authorization scope. Any mismatch, ambiguous authority, projection drift, or unavailable authority fails closed and becomes a typed blocker; no last-writer-wins or model-selected precedence is permitted.

## Automated code-quality gate

- Treat type checking, lint/static analysis, dead-code analysis, architecture validation, and tests as one mandatory quality pipeline; unit tests alone are not a substitute for static checks.
- Validate proposed content in an isolated overlay before every harness-mediated modification. After every atomic modification, run all applicable fast incremental checks to a terminal pass/fail before the next dependent model step or modification. A failed/unavailable required check blocks further work except a declared scoped repair; run the canonical full gate before completion.
- Detect invalid or nonexistent functions/constants/variables, unused locals/parameters/imports/exports, dead files and dependencies, unreachable statements, constant/dead-end branches, duplicate or impossible conditions, switch fallthrough, inconsistent returns, unsafe narrowing, circular dependencies, and forbidden module-boundary crossings.
- Enforce strict language/compiler settings and fail closed on diagnostics; do not suppress errors with broad ignores, unsafe casts, or blanket exclusions.
- Add project-specific checks for central-config drift, duplicate policy/constants, schema/migration integrity, append-only audit invariants, state-machine transitions, rollback integrity, MCP/subagent contracts, and transport/service boundary parity.
- Maintain focused unit and regression tests for every behavior or repaired defect, plus integration and end-to-end CLI workflows.
- Use property-based/state-machine tests where input/state combinations are large, especially steering, concurrency, event ordering, checkpoints, and rollback.
- Enforce meaningful branch/function/line coverage thresholds, but never treat coverage percentage alone as test quality.
- Use mutation testing or an equivalent fault-injection score on critical modules to prove tests fail for realistic coding mistakes and weakened assertions.
- Record which checks ran, versions/config, duration, diagnostics, skipped checks, and results in the trace. The agent cannot claim completion when a required gate failed or did not run.
- Research and select latest-stable tools against the actual stack; avoid redundant analyzers and document any necessary version constraint.
- Reconcile the detected changed-file/symbol set, editor postconditions, compiler/static diagnostics, and required test inventory after each modification. An applicable check may never be skipped for convenience, latency, model context pressure, or cost; a true capability gap blocks and asks the user.

### Reusable multi-language quality packs

- Implement project-agnostic quality packs as pluggable modules. The core owns orchestration and a normalized diagnostic/result schema; language/tool details stay behind pack interfaces.
- A pack declares language/runtime detection, supported file/project markers, capability categories, latest-stable tool resolution, prerequisites, commands, configuration discovery, output parsers, safe-fix policy, timeouts/resources, cache/freshness inputs, and deterministic required/not-applicable status. A capability that applies to a supported changed artifact is required; unavailable required capability blocks and asks the user.
- Reuse and respect an existing project's compiler/linter/test configuration before generating or changing configuration. Never install a competing tool merely because a default pack lists it.
- Normalize diagnostics to stable fields: pack/tool/version, category, severity, code, file/symbol/range, message, evidence, suggested action, auto-fixability, execution status, duration, and source artifact hash.
- Standard cross-language capability categories include parse/build/type/reference validity, undefined names/symbols, unused/dead code and dependencies, unreachable/constant/duplicate branches, return/control-flow consistency, cycles and architecture boundaries, formatting/lint/security, test/regression coverage, property/state tests, and mutation/fault-injection quality.
- Every pack ships a versioned defect-fixture matrix (a small “bug zoo”) proving which mistakes it catches and recording false positives/unsupported categories. A passing pack test requires expected diagnostics, not only a zero exit code.
- Test packs in isolated fixtures and never let analyzers mutate user code unless a separately previewed fix is approved.
- Detect applicable packs dynamically and compose a generic baseline with project-specific invariant packs. Record pack selection and every not-applicable/unsupported capability with deterministic evidence; unsupported required coverage blocks and cannot be recorded as a skip/pass.
- Build the framework and fully tested packs for languages actually detected in the user's repositories first; expand the catalog from measured demand rather than prebuilding every ecosystem.
- Evaluate packs by detection recall/precision, incremental and full-run latency, deterministic output, maintenance health, license/privacy, setup burden, and compatibility with provider-agnostic agents.

## Agents and research

- Subagents are first-class, named, typed, centrally configurable roles rather than hard-coded branches.
- Configurable fields include instructions, capabilities/tool allowlists, MCP access, model/provider override, read/write scope, concurrency, total fan-out, depth, context/token/cost budget, heartbeat/lease/recovery, timeout, cancellation, and routing rules. Configuration may narrow privileges or budgets but cannot remove inherited root policy or mandatory gates.
- Delegate every model-visible repository/file read, directory listing, exact/lexical/semantic search, and codebase discovery operation to a dedicated read/discovery subagent. The orchestrating/parent model receives bounded evidence summaries and stable evidence pointers, never a direct raw read/grep/glob tool path. Deterministic harness internals may read bytes only through the audited repository gateway for validation/indexing and do not expose an alternate model capability.
- Expose every model-callable tool—including repository reads/search, editor, shell/process, quality, Git, agents, research, memory, and introspection—only through a harness-owned MCP gateway with normalized schemas, authorization, audit, idempotency, and health checks. Raw read/grep/glob/shell/provider tool endpoints are not present in any model or subagent tool allowlist, so MCP use is structural rather than a prompt preference.
- Every build/change/investigation uses agents and the MCP gateway. If a required read agent, research agent, MCP server/gateway capability, repository index, or validation capability is absent, unhealthy, unauthorized, or schema-incompatible, block before dependent work, disclose the exact gap, and ask the user; never fall back to a raw tool or model memory.
- For every uncertain or current external fact, dispatch research agents through Context7, DeepWiki, Kagi, and Scrapling. Each service provides a complementary evidence lane; their results participate in the mandatory independent triple-verification/reproduction record. If a required service cannot safely or validly serve the query, record why it is required but unavailable, mark the finding unknown, block dependent work, and ask the user rather than omitting it silently.
- Inject the immutable effective root policy—including MCP-only access, read delegation, current research, triple verification, reuse discovery, attempt lookup, audit, mutation safety, and user-question rules—into every agent at creation/resume/compaction. Mechanically attest the effective policy and capability set; agent-authored instructions cannot override or shadow it.
- Record every delegation, prompt, result, error, token/cost event, cancellation, and handoff in the shared trace.
- Do not claim research or repository coverage unless tool evidence proves it.
- Every build/change request begins with two explicit gates before design or edits: (1) current whole-repository reuse discovery and (2) current external research.
- External research must use live web/MCP evidence rather than the model's training-memory claims for best practices, security guidance, latest-stable frameworks/libraries, language/runtime choice, architecture, and implementation patterns relevant to the task.
- Prefer primary sources: official documentation, specifications, release notes, maintained repositories, and original research. Use secondary sources only for comparison or unresolved field evidence.
- Record source URL/identity, retrieval time, publication/release/version date, applicable version, supported claim, confidence, and contradictions.
- Research breadth above the mandatory four-service, triple-verification, reproduction, and affected-stack/API floor is task- and risk-aware but never omitted: a local bug fix still verifies the active stack and affected API; a new subsystem compares viable languages/frameworks/implementations before selection.
- Cache verified research artifacts to reduce repeated payload retrieval, but every build/change still performs a live four-service source/version/freshness check and records it. Cached claims satisfy the current gate only after live revalidation confirms unchanged applicable source, stack, version, security, and task context; any change invalidates and reruns full verification.
- When required current-research capabilities are unavailable or disagree, stop before implementation, mark the affected finding unknown, disclose the evidence and gap, and ask the user whether/how to proceed. Never silently fall back to model memory or let the model resolve the contradiction by confidence alone.
- The implementation plan must show how local reuse evidence and external research changed or confirmed the chosen approach.

## Live shared multi-agent memory and coordination

- All agents working on a project share one persistent, live-updating, provider-neutral project memory and coordination plane backed by the append-only event journal.
- Do not inject the entire global history into every prompt. Give each agent a bounded relevant snapshot plus subscribed deltas, with on-demand evidence retrieval by stable ID.
- Shared state includes agent roster/heartbeat/status, task graph and dependencies, ownership/leases, base revision, planned file/symbol touch set, discoveries, reuse candidates, decisions and rationale, assumptions/questions, source evidence, tool results, code changes/checkpoints, verification results, blockers, and handoff summaries.
- Agents must publish task intent and expected touch set before editing, read current conflicting claims/deltas before each mutation phase, and publish completion/cancellation/failure explicitly.
- Use atomic compare-and-swap claims with expirations, heartbeats, cancellation, and safe lease recovery. A lease coordinates ownership but never overrides file hash/version checks.
- Run concurrent writers in isolated workspaces/worktrees. Integrate through a coordinator that compares base/current hashes, detects overlapping semantic/file changes, runs required gates, and either merges safely or requests a decision.
- Detect conflicts at task, file, symbol, schema/config, migration, and test-fixture levels; do not rely only on path locks.
- Separate durable project knowledge/decisions from ephemeral run status. Summaries are derived projections with source-event pointers, never replacements for raw evidence.
- Redact secrets and apply project/workspace isolation so “global” coordination never leaks unrelated project or user data. Cross-project knowledge, if enabled later, is an explicit separately scoped store.
- “Global” means all authorized agents and harness components within one declared project/root workflow; unrelated projects, users, tenants, and raw private sources are isolated by default and require separately authorized stores and indexes.
- Apply a field-level authority matrix: agents may append attributed observations, hypotheses, requests, and proposed state transitions, but only deterministic coordinators/gateways may verify evidence, change authoritative lifecycle/task/lease/config/checkpoint/gate state, resolve conflicts, or publish derived current projections. No agent may confirm its own evidence, finish another owner’s task, release another lease, or upgrade an interpretation into a fact.
- Preserve causality and idempotency for all updates; reconnecting agents replay missed events from a cursor and cannot duplicate a completed mutation/handoff.
- Tests must reproduce simultaneous non-overlapping work, overlapping file/symbol edits, stale bases, expired agents, cancellation after mutation, conflicting config/migration changes, handoff visibility, reconnect/replay, malicious/stale attempts to forge evidence or authoritative state, prompt-injection memory content, cross-project access, and deterministic integration outcomes.

### Live harness self-model and global awareness

- Maintain an authoritative structured runtime self-model so every agent can discover what the harness is, what it is doing, and what capabilities/actors are currently available; never rely on a static prompt or model memory for runtime facts.
- Include harness/build/schema/config fingerprint, current project/feature/lifecycle state, task graph/plan, active attempt and acceptance gates, base revision/worktree/dirty state, checkpoints, memory/event cursors, repository-index status/freshness, research-cache status, and unresolved decisions/blockers.
- Maintain a live agent registry with configured roles, instructions/capability scopes, provider/model assignment, current status/task/ownership/touch set, progress, dependencies, heartbeat/lease, context/compaction state, last result, and blocked/cancelled/failure reason.
- Maintain a live capability registry for local tools, file editor strategies, MCP/research servers, quality packs/analyzers, providers/models, storage/backends, and integrations. Record schemas, versions, health, permissions/approval mode, limits/rate/cost budget, supported features, startup/recovery state, and evidence freshness.
- Discover and health-check capabilities at startup, task preflight, reconnection, and after configuration/plugin changes. A configured capability is not considered available until its current health/schema/capability probe succeeds.
- Give agents a bounded relevant snapshot at start/resume/compaction and publish ordered deltas thereafter. Agents can query full structured state and evidence by stable ID; do not broadcast an ever-growing global prompt.
- Before planning or dispatch, mechanically verify that required agents/tools/MCPs/provider features/quality packs are healthy and authorized. Missing/degraded capability creates a typed blocker or user decision, not a silent fallback.
- Expose provider-neutral introspection through reusable service methods/tools/resources and CLI views such as status, feature, plan, agents, tasks, capabilities, tools, MCP, quality, index, memory, attempts, checkpoints, and blockers; the later web UI consumes the same model.
- All registry/state changes are append-only events with causality, actor, timestamps, prior/new state, and health evidence. Derived current-state projections are rebuildable and cannot silently drift from the event source.
- Tests cover hot add/remove/upgrade, schema change, health degradation/recovery, agent crash/stale heartbeat, permission change, provider capability mismatch, index staleness, compaction/resume, concurrent updates, delta replay, and deterministic snapshot reconstruction.

### Searchable attempt/experiment ledger

- Make every substantive investigation, command, research query, tool call, edit strategy, build/test run, and retry a durable attempt record; negative and inconclusive results are first-class shared knowledge.
- Attempt records contain stable ID and lineage, feature/task/agent, objective and hypothesis, expected result, start/end state, repository/base/checkpoint hashes, file/symbol targets, environment/runtime/dependency/config fingerprints, provider/model, tool/schema version, sanitized exact arguments, timestamps/duration, tokens/cost, side effects/diffs/artifacts, stdout/stderr/result hashes and retained evidence pointers, typed error, verification, and observed verdict.
- Separate observed facts from agent interpretation/root-cause hypotheses. Later evidence may supersede an interpretation without rewriting the original attempt.
- Final states are explicit: succeeded, failed, inconclusive, blocked, cancelled, superseded, or rolled back. Pending/running attempts require heartbeat/lease recovery and cannot silently disappear after compaction or agent death.
- Before any new attempt, retry, or materially similar tool call, the coordinator performs a mandatory search by intent, target file/symbol, tool, error signature, feature, and context fingerprint. The retrieved evidence is attached to the plan/trace.
- If an equivalent attempt already ran in an unchanged context, reuse its result or block the duplicate. A retry requires a recorded strategy/context delta or an applicable centrally configured transient-retry policy.
- Canonical request fingerprints and idempotency keys prevent duplicate executions across agents/reconnects. Concurrent equivalent attempts are coalesced or explicitly approved as independent reproduction.
- Context fingerprints prevent false reuse: changes to relevant source hashes, environment, inputs, dependencies, configuration, permissions, provider/model/tool versions, or test fixtures mark earlier conclusions as potentially stale and trigger revalidation.
- Search uses exact structured indexes plus full-text and optional semantic/graph retrieval. Results must remain explainable, with stable evidence links and relevance/context-match reasons; semantic similarity alone never blocks an attempt.
- Store large outputs/artifacts in a redacted content-addressed evidence store with bounded prompt previews. Retention/compaction policies are central config, preserve hashes/metadata, and never discard an unresolved attempt's only evidence.
- After prompt compaction, resume, or handoff, reconstruct agent context from current feature state, unresolved decisions, relevant recent deltas, and attempt summaries/evidence pointers rather than relying on transcript recall.
- CLI/web views expose attempt history, filters, lineage, context differences, repeated/futile loops, evidence, side effects, and “why is this retry allowed?” explanations.
- Tests cover compaction/restart persistence, cross-agent discovery, exact duplicate suppression, transient retry, changed-context revalidation, false semantic matches, pending-attempt recovery, concurrent coalescing, superseded hypotheses, secret redaction, evidence retention, and deterministic search ordering.

### Federated exact, semantic, and graph retrieval

- Build one provider-neutral retrieval service over the redacted operational memory, requirements/policies, events, attempts, tools/results, agent/task handoffs, research, quality evidence, and code-intelligence indexes. Preserve source-specific adapters and stable evidence pointers.
- Use multiple complementary lanes: structured exact filtering for IDs/state/time/repo revision/agent/tool/error/context; lexical/full-text BM25 for deterministic terms/symbols; semantic/vector retrieval for concepts/paraphrases; and graph traversal for causality, lineage, dependencies, conflicts, supersession, and impact.
- Keep source-code intelligence specialized (for example CodeGraph) and federate its results rather than flattening code structure into only a generic embedding store.
- Apply structured project/access/time/context filters before or during retrieval, not after leaking cross-project candidates. Index only redacted authorized projections; never embed plaintext secrets/full-fidelity vault payloads.
- Local/private source, transcript, prompt, diff, event, or evidence content may be processed only by local approved retrieval lanes by default. A hosted embedding, rerank, search, or analysis service receives it only after the private-data egress approval defined in the security boundary; credentials or general provider access do not imply that approval.
- Normalize ranked results with source type, relevance lane/scores, context/freshness match, evidence ID/hash, excerpt/summary provenance, access decision, and why it was returned. Preserve lane scores; do not hide a semantic guess behind one opaque score.
- Fuse lanes with a deterministic configurable method (for example reciprocal-rank fusion) and optional separately evaluated reranker. Exact IDs/current-context matches and causal links outrank semantic similarity for control decisions.
- Semantic/vector results are discovery evidence only. They cannot alone block a new attempt, approve an edit, declare equivalence, resolve a conflict, or mark a requirement satisfied; deterministic verification follows retrieval.
- Support query planning from natural language plus explicit structured filters, typo/synonym/code identifier handling, temporal ranges, negation, “current versus superseded,” and bounded query expansion. Log every generated query and result set so poor retrieval can be diagnosed.
- Benchmark serious latest-stable local/hostable engines and combinations rather than selecting from claims. Include a deterministic embedded lexical/structured baseline and evaluate hybrid/vector/graph candidates only when their added recall justifies setup, latency, privacy, and operational cost.
- Before executing/scoring candidates or inspecting candidate outcome data, preregister candidate identities and inclusion/exclusion rules, sanitized ground-truth corpus/version, query set and holdouts, lane configurations, required repetitions, metric formulas, weights, minimum thresholds, zero-tolerance isolation/correctness invariants, tie-break rules, resource/privacy ceilings, and disqualification rules in a content-hashed immutable benchmark plan. Changing the plan creates a new benchmark version and invalidates cross-version ranking claims.
- Build an evidence-backed ground-truth suite from real sanitized harness data and known relationships, supplemented by adversarial/synthetic controls. Labels/oracles cannot come only from the same LLM being evaluated.
- Required metrics: Recall@k, Precision@k, MRR, nDCG, zero-result/false-positive rates, exact/filter/temporal/negation/supersession correctness, context-match accuracy, incremental visibility latency, query/index latency, index size/build cost, output tokens, concurrent determinism, restart/recovery, stale/corrupt index behavior, and cross-project/secret isolation.
- Test query classes include exact IDs/symbols/errors; paraphrased prior attempts and decisions; similar-but-different contexts; failed versus successful outcomes; changed revisions/configs; tool/result chains; agent handoffs; contradictions/superseded policies; code reuse/impact; and “what was already tried and why.”
- Stress with large/high-churn event corpora, many agents/readers, incremental writes/deletes/retention, compaction, malformed documents, prompt-injection text, Unicode/typos, duplicate content, conflicting evidence, and unavailable embedding/rerank services.
- Expose search health, corpus/version/cursor, index freshness/lag, lane availability, embedding/model/version, and degraded behavior through the live capability registry. Required pre-action searches fail visibly when mandatory lanes are unhealthy.
- No weighted average can hide a violation of access isolation, secret handling, exact-ID correctness, current-context filtering, deterministic control decisions, or required-lane health; those are zero-tolerance disqualifiers. Rank only candidates that pass every preregistered floor and publish raw per-query results, uncertainty, worst case, and resource/privacy costs.

## Repository intelligence and reuse gate

- Evaluate `codebase-memory-mcp` as the baseline; it has not worked well enough in the user's experience.
- Find, install in an isolated test environment when authorized, test, and rank current replacements.
- Benchmark on the user's real repositories, not vendor demos.
- Required dimensions: full-repository coverage, symbol/reference/relationship accuracy, reuse-candidate recall, semantic and exact search, incremental freshness after edits, multi-language support, dirty-worktree behavior, latency, output/context size, local privacy, setup/runtime cost, MCP reliability, maintenance health, and latest-stable availability.
- Before candidate execution, preregister repository fixtures/versions, eligible-file manifest rules, candidate inclusion/exclusion, queries/holdouts, ground-truth reuse/relationship labels, repetitions, metric formulas, weights, minimum thresholds, zero-tolerance wrong-repository/empty-current/stale-current/cross-project failures, tie-breaks, privacy/resource ceilings, and disqualification rules in an immutable benchmark plan.
- Rank sustained per-repository reliability above one-time cold-start speed. A bounded bootstrap/provisioning step is acceptable when subsequent behavior is deterministic and maintainable.
- Measure cold bootstrap separately from warm start and steady state. Repeat activation/query tests across process restarts, working directories, concurrent clients, dirty changes, index updates, and host/sandbox boundaries.
- Require unambiguous repository identity, health/status visibility, stale-index detection, automatic or guided repair, persistent daemon/cache lifecycle, and evidence that a valid index remains discoverable after restart.
- Disqualify tools that silently return an empty/unindexed project, cross-contaminate projects, serve stale results as current, or require recurring manual recovery even when their headline latency is low.
- Before **every** atomic modification—not only creation—the harness refreshes/reconciles and queries the current whole-repository structural/semantic index for analogous logic, affected relationships, and reusable/adaptable candidates, then attaches concrete file/symbol evidence and the reuse/adapt/create decision to the approved change set. Any prior modification invalidates affected index state, so a feature-start search cannot substitute for the current per-modification gate.
- The harness pre-change gate must cover every artifact category listed by the reuse requirement—including constants, types, tests, commands, adapters, policies, components, migrations, and config keys—not only new modules/functions/schemas/workflows.
- “Whole codebase in one go” means one complete, current, repository-identity-bound maintained index/map plus targeted evidence retrieval in one gate; it does not mean injecting all source text into one LLM prompt. The manifest explicitly classifies tracked, dirty, untracked, ignored, generated, vendored, binary, LFS, submodule, worktree, and symlink content, and the gate reports every excluded/unsupported class rather than silently claiming completeness.
- Prove coverage by reconciling the current index inventory and content hashes against the authoritative repository manifest immediately before the gate. Any wrong-root, missing eligible file, stale dirty/untracked change, silent empty result, or unresolved exclusion blocks and asks the user.
- If no candidate meets the benchmark, implement the smallest pluggable repository-index adapter rather than coupling the harness to a weak server.

## Provider-agnostic file-edit capability and benchmark

- Select or build a harness-owned, provider/LLM-agnostic file-edit capability whose correctness does not depend on a model having memorized a proprietary patch syntax.
- Research and benchmark current edit protocols/tools (structured exact replacement, unified/apply-patch variants, range/hash edits, AST/LSP/symbol edits, and transactional multi-file editors) from primary sources and maintained implementations.
- Use the actual retained OpenCode history to establish baseline edit/write/patch tool-call validity, retries, errors, partial changes, and outcomes by provider/model/variant without issuing new paid calls.
- Run a prospective controlled multi-LLM benchmark only with explicit provider/cost/usage authorization. Give each model only the tool schema/description and task context; do not teach model-specific hidden syntax.
- Before any candidate run, preregister candidate inclusion/exclusion and maintained-version criteria; language/file/scenario/model/provider matrices; repetitions and stochastic settings; metric formulas, weights, minimum floors, confidence/variance treatment, worst-case gates, zero-tolerance safety failures, tie-break rules, privacy/cost/resource ceilings, and disqualification rules in a content-hashed immutable plan. Changing a threshold or weight after seeing results starts a new benchmark version and cannot retroactively change the earlier winner.
- Benchmark across representative languages and file forms: simple and repeated text, multi-location change, import/symbol edits, nested syntax, large files, new/delete/move, multi-file atomic changes, whitespace/Unicode/CRLF, stale hashes, concurrent edits, dirty worktrees, path spaces, symlink/path traversal, generated/minified files, syntax-invalid proposals, partial failure, retry, and idempotent replay.
- Required metrics: first-call schema validity, tool-call error rate, intended-change precision/recall, unrelated churn, parse/type/build/test success, retries and recovery rate, stale/conflict safety, atomicity/rollback, idempotency, token/context size, latency, model/provider variance, and final code-quality gates.
- Also score maintenance/release health, license, supply-chain/provenance, install/offline behavior, dependency footprint, schema stability, accessibility from the MCP gateway, and long-term provider/language compatibility. Wrong-file writes, path escape, partial atomic commit, undetected corruption/truncation, audit bypass, lost rollback, or false success are zero-tolerance disqualifiers and cannot be averaged away.
- Prefer a small self-describing discriminated schema with stable paths, expected content hashes/base revision, exact or symbol anchors, explicit create/update/move/delete operations, dry-run preview, idempotency key, and an atomic change-set boundary.
- Return machine-actionable errors containing stable codes, current hashes, ambiguity candidates/locations, failed operation index, safe retry guidance, and rollback status. Never silently choose among multiple matches or partially commit an atomic change set.
- Separate planning from mutation: the reuse/research gates and shared coordinator approve a proposed change set; the editor applies only that bounded set and emits before/after hashes, diff, checkpoint, and diagnostics.
- Every filesystem-writing path—including the primary editor, shell redirection, commands/processes, formatters, code generators, package managers, compilers with emitted files, Git operations, scripts, plugins, subagents, MCP servers, remote tools, migrations, and test side effects—runs in a harness-owned isolated overlay/worktree through the same mutation gateway. The gateway inventories all resulting writes, applies allowed-path/diff/postcondition and quality checks, and atomically promotes the accepted change set; direct authoritative-worktree write capability is absent.
- A tool that cannot run inside the overlay or whose writes/side effects cannot be completely inventoried is declared unsupported for mutation, blocked, and presented to the user as a capability/irreversibility decision. Merely logging an uncontrolled write never satisfies the mutation boundary.
- Optional AST/LSP strategies may improve language-specific edits behind the common interface, but the public contract and audit events remain language/provider neutral.
- If no existing tool is reliable across the measured matrix, implement the smallest modular editor behind this contract and rerun the same benchmark. Do not claim “best” without comparative measured evidence.
- Treat a tool-level `completed` status as insufficient. The editor must internally re-read every affected file, compute authoritative before/after hashes and Git-compatible diff, and compare the actual change set with the approved proposal before reporting success.
- Each operation declares postconditions such as expected match count, exact replaced/inserted/deleted region, expected old-text absence/new-text presence, symbol/range identity, and allowed files/regions. Verify every postcondition independently after write.
- Detect and reject over-broad replacement, under/partial replacement, unintended deletion, duplicated insertion, wrong occurrence, truncated content, unchanged/no-op result, unexpected formatting/line-ending churn, unapproved file changes, and parse-invalid output.
- An atomic edit whose actual diff or postconditions deviate from the proposal automatically restores its checkpoint and returns a typed mismatch report. Never leave a partial “failed” transaction for the LLM to discover later.
- Return bounded post-edit context, full diff/evidence pointer, per-operation applied/matched counts, diagnostics, and actionable retry candidates to the model. Require acknowledgement of the verified diff before a subsequent dependent edit.
- Add differential/fault-injection tests that deliberately simulate the historical OpenCode edit failures: extra-range deletion, prefix-only replacement, repeated-snippet ambiguity, stale context, silent no-op, partial multi-file write, formatter expansion, content truncation, path confusion, and tool-reported success with corrupted output.
- Historical benchmarking must inspect semantic diff correctness and later user/model corrections, not only recorded tool state. Correlate successful edit calls with immediate re-reads, later repair edits, tests/static diagnostics, and final file/diff state where retained.
- Render proposed edits into an isolated in-memory/temporary overlay first. Do not mutate the working tree until applicable language/config quality packs accept the candidate content.
- For supported languages and structured formats, pre-apply checks include parser/compiler syntax, bracket/delimiter balance, required punctuation, indentation-sensitive grammar, imports/name resolution, incremental type/reference diagnostics, and configured formatter/linter structural validity. If a required checker cannot provide one of those applicable guarantees, the language/capability is unsupported for safe mutation and the edit blocks for a user decision.
- Missing brackets, braces, parentheses, colons, commas/terminators, malformed indentation, unterminated strings/comments, invalid declarations, nonexistent symbols, and newly introduced type errors must reject the candidate before the real-file transaction.
- Compare baseline and candidate diagnostics. If the baseline is already invalid, allow only a scoped repair whose declared target diagnostics are removed and which introduces no new equal-or-higher-severity diagnostics; preserve both diagnostic sets as evidence.
- Unsupported language or unavailable required parser/type checker is an explicit capability gap. The editor cannot claim syntax safety or apply unchecked code; it blocks the mutation, records the unknown guarantee, and asks the user whether to cancel, add a properly researched/tested quality capability, or change scope.
- After pre-apply acceptance, write atomically, re-run the same checks against the actual filesystem content, compare hashes/diff/postconditions, and roll back on any discrepancy between overlay and committed result.
- Include syntax/indentation/name/type defect fixtures for every language quality pack and run them against every editor strategy/model benchmark combination.

## Interaction and steering

- Preserve all user inputs in order, including steering/addenda submitted while a turn or tool phase is active.
- Correlate each input to the active turn and make its disposition visible: queued, merged, superseding, answered, or unresolved.
- Do not leave progress promises, tool phases, cancellations, or mutations without explicit terminal state.
- Incorporate corrections immediately and completely; surface which constraints changed the plan and code.
- Avoid making the user repeat stable engineering preferences.
- Treat actual code quality and steering alignment as higher-priority design evidence than provider-error frequency.
- CLI acceptance tests inject user input while the provider is streaming, a tool/subagent is running, an approval is pending, cancellation is racing, and restart/resume is occurring. They prove ordered durable capture, one visible disposition per input, no drop/duplication, explicit terminal state, and identical authorization/lifecycle behavior through the transport-neutral service.
- Treat all model/tool/repository text as untrusted at rendering boundaries. Escape or neutralize terminal control/ANSI sequences and, in the later web client, HTML/script/URL injection while retaining authorized raw bytes only in protected evidence.

## Data classification, privacy, and external egress

- Classify every payload and derived artifact before access or egress as public, project-private, user-private/conversation, credential/secret, regulated/restricted, or explicitly declassified/redacted. Classification propagates through prompts, summaries, diffs, embeddings, caches, logs, fixtures, and exports; an unknown class is treated as the most restrictive applicable class.
- Local code, repository metadata, diffs, prompts, logs, user inputs, OpenCode conversations, evidence, and private derived summaries remain local by default. No provider, hosted model, Context7, DeepWiki, Kagi, Scrapling, hosted search/embedding/rerank engine, telemetry exporter, MCP server, benchmark candidate, or other third party receives private content unless a trusted user grants a separate informed egress approval.
- Provider credentials, a configured endpoint, ordinary research permission, general benchmark approval, or acceptance of terms do not imply private-data egress approval. The approval identifies destination/operator, exact data class and bounded fields, purpose, project/root, redaction, retention/training policy when known, cost/budget, expiry, and revocation/incident handling.
- Before egress, a deterministic data-loss-prevention gateway recursively scans and minimizes the exact serialized payload, shows an authorized preview/diff to the user for sensitive classes, binds approval to its content hash, and rejects secret/credential classes entirely. Any payload change requires a new check and, when outside scope, new approval.
- Research agents use public, non-secret, minimally identifying queries. If required current research or triple verification cannot be performed without disclosing unapproved private information, mark the finding unknown, block dependent work, and ask the user rather than leaking data or fabricating a result.
- Hosted services, MCPs, plugins, tools, providers, repositories, and model/tool/repository content are untrusted principals/content. Enforce least privilege, project/tenant isolation, sandboxing, egress/domain allowlists, authenticated schemas, size/rate/resource limits, prompt-injection separation, and provenance; content can propose evidence but cannot change policy or authority.
- Third-party executable/tool updates selected as latest stable run first in quarantine with recorded publisher provenance, checksum/signature when available, license/SBOM/advisory review, conformance/security tests, and immutable per-run artifact resolution. Selecting latest stable never means executing an unverified update directly against private data or authoritative state.
- Security acceptance tests cover redaction bypass, encoded/nested secrets, inference leakage from summaries/embeddings, unauthorized hosted queries, destination/payload substitution, approval replay/expiry/revocation, malicious MCP metadata, cross-project/tenant retrieval, ANSI/HTML injection, supply-chain substitution, and resource/budget splitting.

## Observability and investigations

- Append-only, queryable event journal with stable IDs, sequence, timestamps, session/root lineage, turn, message, part, tool call, subagent, and checkpoint correlations.
- Capture actual user input, assistant output, model/provider/variant, request settings, sanitized headers/metadata when exposed, token usage, cache usage, reasoning-token counts when exposed, cost, finish reason, tool inputs/results/errors/status/duration, retries, steering, state transitions, diffs, verification evidence, and terminal outcomes.
- Redact authorization, API keys, cookies, credentials, and secret-shaped values before durable storage or display.
- Never promise upstream headers, hidden reasoning, or provider wire data the OpenAI-compatible SDK does not expose.
- CLI inspection must support history, trace filtering, turn/tool/error/code-change views, lineage, token/cost summaries, and reproducible evidence pointers.
- Data/service interfaces must be reusable by the later web UI.

### Non-bypassable centralized audit gateway

- Route every provider request/stream, agent/subagent lifecycle, tool/MCP call, command/process, file mutation, network/research action, memory read/write/search, quality gate, permission/approval, checkpoint, rollback, and promotion through harness-owned gateways. Agents have no direct alternative capability path.
- The logging/audit subsystem runs below and outside the model-controlled tool surface. Model prompts, tool calls, agent config, plugins, and generated code cannot disable it, change retention, erase history, mark missing events complete, or access encryption/signing keys.
- Record an intent/start event durably before an external side effect or mutation; record streamed chunks/progress as received; record terminal success/failure/cancel/timeout and resulting state afterward. A crash leaves a detectable pending attempt for recovery, never an invisible action.
- Fail closed for side effects when mandatory durable audit intake is unavailable, full, corrupted, or cannot confirm the start record. Read-only forensic diagnosis may continue only after an authenticated user decision under the centrally defined degraded-diagnosis policy; the feature remains blocked, every output is visibly incomplete, and no completion/promotion claim is allowed. This is a diagnosed containment state, not a fallback execution path or workaround.
- Capture full correlation context: trace/span/event/request/session/root/feature/task/attempt/turn/message/part/tool/call/agent IDs; agent role/name/provider/model/variant; parent/child/handoff; project/workspace/worktree/base/checkpoint; actor and authorization; wall and monotonic timestamps; queue/start/end/duration; retry/idempotency; state transitions; status and health.
- Capture the exact data exposed to the harness: user/system/policy messages; provider request options and serialized body; tool schemas; sanitized and sealed headers/metadata; streamed model output and final response; token/cache/reasoning usage and cost; tool/MCP inputs, progress, outputs, attachments, errors and stack/cause; stdout/stderr/exit/signal; files/diffs/hashes; research queries/sources; memory retrievals; quality diagnostics/tests; approvals and promotion evidence.
- Preserve full large payloads as chunked, content-addressed evidence blobs with hashes and event pointers instead of truncating the authoritative record. Prompt/CLI views use bounded previews but can retrieve authorized full evidence.
- Protect secrets/private data with two views: an encrypted, access-controlled full-fidelity evidence vault and a recursively redacted searchable operational projection. Never store authorization, cookies, API keys, OTP seeds, private keys, or secret-shaped values in plaintext logs.
- Models, agents, plugins, MCP servers, search indexes, and routine prompts can access only least-privilege redacted operational projections by default; they have no tool for arbitrary full-vault reads. Human/full-vault access requires an authenticated principal, purpose, project/evidence scope, time limit, and a separately audited decision.
- Log redaction/encryption decisions as metadata without echoing matched secrets. Keys live outside model-accessible config/files and support rotation, access auditing, and least-privilege roles.
- Encrypt or otherwise prevent recoverable plaintext across the complete evidence lifecycle, including intent buffers, WAL, temporary/spill files, content-addressed blobs, indexes/caches, crash/core dumps, swap where controlled, backups, exports, and deleted-file remnants. Startup/preflight verifies the protection or fails closed for sensitive intake.
- Make the journal append-only and tamper-evident using sequence/causal checks, canonical serialization, chained hashes or Merkle checkpoints, restricted storage permissions, and optional signed/WORM exports. Derived projections can be rebuilt and verified.
- Use durable local buffering/WAL, backpressure, idempotent ingestion, crash recovery, and deterministic per-stream ordering. Preserve original wall time plus monotonic ordering; identify clock source/skew.
- Instrument adapters with trace/span semantics compatible with an observability standard such as OpenTelemetry, but keep the internal event/evidence contract as the source of truth so no vendor is required.
- Mediate network egress, subprocess execution, filesystem writes, and dynamic/plugin tools so bypass attempts are denied and audited. Capability health checks must verify that no unwrapped side-effect path is exposed.
- Explicitly report observability gaps: hidden provider reasoning, provider-internal operations, response headers/body fields not exposed by the SDK/transport, external side effects outside the harness boundary, or expired/unavailable source evidence. Never label such traces complete.
- Provide indexed queries and monitors for every correlation dimension, error/success/latency/token/cost, repeated attempts, pending/orphaned state, agent/tool/provider health, file/code history, approvals, test/promotion evidence, and audit gaps.
- Stress and adversarial tests cover attempted logger bypass/disable/delete, direct egress/tool access, malformed/oversized/binary streams, concurrent events, partial writes, crash between start/result, disk full, DB busy/corruption, logger outage/recovery, duplicate/reordered delivery, clock skew, key rotation, redaction regressions, unauthorized evidence access, tampering, replay verification, and sustained high-volume retention.
- Reconcile append-only integrity with retention and authorized erasure through append-only tombstones plus destruction of separately encrypted payload keys/blobs where policy or law requires it. Preserve non-sensitive hashes/causal metadata sufficient to prove an erasure occurred without retaining the erased plaintext; erasure itself requires trusted approval and is audited.
- An end-to-end audit completeness oracle inventories every provider/network/process/filesystem/Git/memory/permission/quality/promotion side effect and requires one durable intent plus exactly one terminal or recoverable-pending lineage and matching evidence hashes. Any observed effect without that lineage is a zero-tolerance release failure.

## Rollback and safety

- Conversation/state rollback uses append-only compensating events or forks and preserves forensic history.
- Harness-mediated file changes require pre-change checkpoints, before/after hashes, changed-file manifests, and stale-write protection.
- Rollback must be explicit, previewable, verified, idempotent, and refuse to overwrite newer unrelated changes.
- Arbitrary commands and external side effects cannot be promised as fully reversible. Strict rollback mode must isolate commands or prohibit unjournaled mutations.
- Never use destructive reset as an implicit undo mechanism.
- Every tool/capability declares before use whether each possible side effect is transactionally reversible, compensatable, isolated/discardable, or irreversible, with rollback/compensation procedure, required checkpoint, stale-state guard, external scope, and approval policy. Unknown classification blocks execution.
- Maintain and test a rollback matrix for conversation/projected state, feature/task/agent state, config versions, files and multi-file transactions, indexes/caches, artifacts, databases/migrations, Git refs/commits, remote pushes/deployments, processes, network/API effects, and evidence erasure. Crash, retry, replay, partial compensation, and newer unrelated work cannot create a false rolled-back state.

## Enforced feature lifecycle and promotion

- Model work as a durable feature/work-item state machine enforced by application code, not a prompt convention.
- Required states: declared, externally researched, repository/reuse mapped, scoped/accepted, implementing, incrementally checked, feature tested, independently reviewed, testing candidate, promoted to testing, integrated/closed; include explicit blocked, failed, cancelled, and rolled-back transitions.
- Before any mutation, require a feature ID, objective, user constraints, acceptance criteria, non-goals, risk level, base revision, expected touch set, applicable research/reuse evidence, required quality packs/tests, owner/agents, and promotion policy.
- The coordinator rejects edits or promotion when required prior states/evidence are absent, stale, contradictory, or tied to a different base revision.
- Treat each logical modification as an atomic change set. Capture an immutable Git-backed checkpoint, tree/diff hashes, trace cursor, agent/feature identity, and incremental-check results before another modification begins.
- **Pending user decision `DEC-GIT-CHECKPOINT-001`:** define whether every atomic logical modification creates (A) a real namespaced Git tag, as the user suggested, or (B) a recommended namespaced harness-owned checkpoint ref/commit with human-visible tags reserved for candidates/releases. Do not silently choose either interpretation. The one central config records the answered per-repository policy, namespace, granularity, signing, retention/garbage collection, and visibility; feature mutation is blocked until this decision is answered for that repository.
- “Modification” means one coordinator-approved atomic change set with a fixed base/config/feature/attempt identity and declared file/symbol/postcondition set; it may contain multiple editor operations but admits no unrelated change. Formatter/generator/test side effects discovered in its overlay are part of the same change set or cause rejection.
- Run fast relevant quality packs after every atomic change. On failure, block the next mutation unless the active work explicitly enters a diagnosed repair substate; never stack unrelated edits on a failing base.
- “Feature complete” requires acceptance-scenario execution, project-specific and generic quality packs, regression tests, static/dead-code/architecture/security checks, meaningful coverage/mutation evidence where required, clean diff/worktree review, and independent reviewer evidence.
- Validate the resulting artifact/behavior itself, not only helper functions, mocks, or command exit codes. Preserve test inputs, environment identity, versions, outputs, and artifact hashes for reproduction.
- Promotion to the configured `testing` branch/environment is a guarded transaction: revalidate base/current state, integrate in isolation, rerun required gates, create the candidate checkpoint/tag, then merge/push only according to explicit repository policy and approval requirements.
- For each repository, the central config and an authenticated user decision define whether `testing` is a local ref, branch, remote branch, deployment environment, or an ordered combination; the target identity, protected-ref rules, merge strategy, credential scope, push/deploy approval, rollback limits, and retention are explicit. Remote push/deploy is an external side effect and never follows merely from a model declaring completion.
- A failed, unavailable, or missing required gate cannot be converted to warning, skipped, or overridden into promotion by any agent or ordinary user approval. The user may authorize cancellation, a scoped repair, a requirement/scope change, or a separately validated correction to a demonstrably faulty gate, but the original failure and feature remain blocked until the current requirement set genuinely passes.
- The CLI exposes feature status, missing gates, checkpoints, evidence, test history, review findings, promotion readiness, and rollback targets; the later web UI consumes the same service/state machine.
- “Best possible” cannot be proven mechanically. The enforceable contract is repeatable, evidence-backed, current, policy-complete code that cannot be promoted while required quality evidence is missing or failing.

## Guarded self-evolution of the harness

- Allow agents to propose and implement harness improvements (quality packs, provider/MCP adapters, tools, modules, policies, schemas, tests, and UI/service capabilities) only through a dedicated privileged evolution workflow.
- Normal project file tools, generic shell/command execution, MCP tools, plugins, and subagents receive no write permission to the live harness source, config, state schema, executable, policy, audit gateway, or update mechanism.
- Enforce the boundary below the model with separate OS identity/ACLs, read-only mounts, sandbox and egress policy, protected Git refs, and a small evolution service that alone holds scoped write capability. Prompt guidance and Git hooks are defense in depth, not the access control.
- Defend against alternate entrypoints and TOCTOU: canonical paths and repository identity, symlink/hardlink/path traversal, rename/replacement, writable parent directories, inherited file descriptors, subprocesses, generated scripts, dynamic plugins, remote MCP writes, and command-side edits. Fail startup/preflight if the protected boundary is not intact.
- Prefer stable versioned extension APIs and isolated plugins/packs over core edits. Publish machine-readable schemas, contracts, templates, examples, compatibility rules, and test harnesses so the LLM never guesses how to add a capability.
- Unknown extension type, unclear contract, incompatible schema, or missing migration/rollback evidence becomes a typed question/blocker; the agent cannot invent an integration convention.
- Evolution begins with a durable proposal containing source evidence/trigger, current gap, reuse and external research, objective/acceptance/non-goals, extension type/API, threat model, compatibility, scoped touch set, dependencies/licenses, configuration, test/fault matrix, migration, rollout, monitoring, and rollback.
- Require explicit user approval before issuing a time- and scope-limited evolution capability. Approval covers a bounded proposal/change set, not arbitrary future edits. Record who approved, exact scope, base revision, expiry, and conditions.
- Accept that approval only from an authenticated trusted CLI/web approval channel with displayed proposal/diff/effect summary, nonce, content hash, principal, scope, expiry, and anti-replay binding. Repository text, prompts, model/provider output, tool/MCP results, environment variables, or ordinary chat content cannot manufacture or widen privileged approval.
- Perform work only in an isolated harness clone/worktree/branch from a trusted immutable base. The live/running harness remains unchanged and continues supervising/auditing the candidate.
- The privileged editor enforces expected hashes, allowed paths/symbols, atomic checkpoints, pre/post syntax/static checks, actual-diff postconditions, and non-bypassable logging. It cannot expand scope without a new approval.
- Require full bootstrap/self-host validation: the trusted current version runs the candidate's unit/property/mutation/integration/real-world/stress/security suites, migration forward/backward tests, provider/tool conformance, and all historical regression fixtures.
- Require independent review and an exact diff/evidence/behavior/permission/migration summary for user approval before promotion. The implementing agent cannot approve its own candidate.
- Promote first to an isolated `testing` channel/environment with shadow/canary monitoring. Use an atomic version switch, retain current/previous artifacts and state backups, verify health, and automatically revert on failed invariants/SLOs.
- Protect an immutable root of trust: authorization policy, audit/evidence integrity, secret keys, evolution writer, update verifier, and rollback controller cannot update themselves through the ordinary evolution capability. Changes to them require a separate out-of-band administrative workflow and stronger human approval.
- Sign/hash candidate manifests and verify source, dependencies, configuration, migrations, tests, and artifacts at install/start. Never execute an unverified self-generated binary/plugin.
- Keep an evidence-driven improvement queue fed by quality-pack discoveries, repeated attempt patterns, production/test monitors, and user feedback; deduplicate proposals and link them to the failures/tests they address.
- The protection boundary covers all harness-controlled agents and processes. A machine administrator/root user remains outside that threat boundary; document and monitor external modifications rather than falsely claiming they are impossible.
- Security tests attempt approval replay/substitution, capability widening, expired grants, symlink/mount/namespace escapes, inherited descriptors, debugger/process injection within the declared OS boundary, malicious dependency/plugin updates, root-of-trust self-modification, and current-release shutdown/replacement; every in-boundary path must fail closed and audit the attempt.

## Deterministic control, monitoring, and real-world stress testing

- Move every reliably controllable logical, mathematical, stateful, safety, validation, scheduling, retry, limit, and policy behavior out of prompts and into typed deterministic modules with explicit invariants.
- Define machine-checkable invariants for state transitions, event ordering/causality, leases/ownership, idempotency, attempt deduplication, checkpoint/diff integrity, rollback, promotion gates, permissions, budgets, redaction, and evidence completeness. Reject invalid transitions regardless of model output.
- Use independent deterministic test oracles. An LLM response may generate candidate inputs but cannot serve as the sole judge that its own plan/edit/test/result is correct.
- Build a sanitized regression corpus from actual observed OpenCode failures, steering losses, edit corruptions, false-green tests, stale assumptions, dropped handoffs, secret leaks, and repeated attempts.
- Test in representative real repositories, real language toolchains, provider/MCP implementations, filesystems, processes, and isolated OS/container/VM environments when behavior depends on them. Never substitute only mocks for an integration that failed in the real world.
- Push supported behavior to configured boundaries: empty/min/max/oversized inputs; huge repos/files/diffs/tool outputs; Unicode/CRLF/long paths/spaces; deep lineage; many turns/compactions; many concurrent agents; token/cost/time/storage limits; and long-running soak conditions.
- Add property-based and model/state-machine tests with reproducible seeds for workflow transitions, concurrency, event replay, steering, attempt matching, editor operations, shared memory, and rollback. Check invariants across generated action sequences.
- Add mutation/fault-injection tests for critical validators and gates so tests prove they detect weakened conditions, removed checks, wrong branches, altered comparisons, partial writes, and corrupted state.
- Add concurrency/linearizability stress: duplicate delivery, simultaneous claims/edits/promotions, stale bases, clock skew, lease expiry, reconnect/replay, cancellation during mutation, process death, and conflicting config/schema/migration work.
- Add failure/chaos cases: malformed or partial provider streams, hallucinated tool names/arguments, MCP schema change/disconnect/hang, rate limit/retry storms, network loss, disk-full/read-only/permission errors, DB busy/corruption/WAL recovery, truncated artifacts, formatter/compiler crash, and lost child-agent responses.
- Add adversarial security cases: prompt injection in repository/web/tool output, path traversal/symlink races, command/argument injection, secret-shaped content in prose/code/diffs/logs, malicious MCP metadata, oversized payload denial, permission escalation, and cross-project memory leakage.
- Test quality packs themselves for false negatives and false positives using real defect fixtures and clean controls. Record unsupported categories rather than treating silence as success.
- Monitor every run with deterministic loop/retry detection, progress/heartbeat watchdogs, tool/provider health, resource use, latency/error rates, token/cost budgets, pending-state age, index freshness, gate status, and orphaned agents/attempts. Apply centrally configured circuit breakers and escalation.
- Run fast checks continuously, targeted real integration tests at feature gates, and broader load/soak/chaos suites on scheduled or pre-release gates. Never run destructive real-world tests outside disposable/isolate environments.
- Preserve versions, configuration, environment fingerprints, random seeds, inputs, outputs, artifact hashes, and timing so every failure can be reproduced and every claimed pass can be audited.

### Minimum three-scenario adversarial evaluation contract

- No function/module/logic/capability is accepted from a single passing example. Every supported behavior requires at least three materially different scenarios, with distinct inputs/context/failure surfaces; repeating the same scenario three times does not satisfy the gate.
- The minimum three-scenario rule is a floor, not a target. Add boundary, negative, adversarial, randomized/property, concurrency, failure-injection, and historical-regression cases proportional to risk and state space.
- Design evaluations to falsify claims and expose failure, not to demonstrate the expected path. Include hidden/holdout scenarios not used while implementing or tuning the capability.
- Test every reusable module in isolation, in composed integration, and through the real CLI/service/provider/tool path. Mocks support deterministic edge cases but never replace retained real-world integration evidence.
- Exercise the harness on isolated copies/worktrees of multiple real projects differing in size, language, framework, layout, existing quality configuration, dirty state, and failure profile. Never endanger the source repositories.
- Exercise genuine multi-turn conversations with corrections/addenda, conflicting instructions, tool failures, cancellations, long turns, context pressure/compaction, restart/resume, subagent handoffs, simultaneous agents, forgotten facts, repeated attempts, and user approval/denial.
- Evaluate across multiple provider/model/variant capability levels, including strong and weaker/unfamiliar models given only public schemas/instructions. Do not tune tools solely to Makora/GLM or the best-performing model.
- Before evaluation, preregister a content-hashed model/provider matrix whose diversity criteria include at least two materially different provider/adapter families when authorized and available, multiple model capability tiers, distinct structured-tool-call behavior, context limits, and at least one weak or unfamiliar model. “Many LLMs” is satisfied by the preregistered diversity dimensions and repeated trials, not by aliases of one underlying model; unavailable paid/private candidates block the claimed matrix and require user budget/egress decisions.
- Prospective paid/provider evaluations require explicit configured credentials, spend/token/time budgets, and approval. Record every attempted run and cost; never silently use the user's provider accounts.
- For stochastic behavior, run repeated trials with recorded seeds/settings and report distribution, variance, worst case, flake rate, confidence, and failure taxonomy. Do not average away a safety/correctness violation.
- Security, authorization, audit integrity, isolation, atomicity, rollback, and state-machine invariants tolerate zero violations. Quality/retrieval/model metrics use explicit thresholds and worst-case gates defined before the test.
- Use independent deterministic oracles wherever possible: exact hashes/diffs, compilers/parsers, state invariants, event replay, expected diagnostics, search relevance sets, artifact behavior, and controlled fixtures. The evaluated LLM never scores its own result.
- Require an independent review synthesis of raw evidence after automated scoring, covering code/diff quality, requirement alignment, unsupported claims, hidden workarounds, skipped tests, and whether the oracle itself was adequate.
- Preserve all runs, including timeouts, malformed calls, partial artifacts, retries, and failed/aborted scenarios. No cherry-picking, deleting outliers, or rerunning until green without retaining prior evidence.
- Any new observed failure becomes a minimized sanitized regression fixture linked to its attempt/evidence and is run in future incremental/full gates.
- Split cadence by cost without weakening release evidence: fast deterministic checks per edit, targeted three-scenario real integrations per feature, broader nightly/continuous stress matrices, and full multi-project/multi-model/chaos evaluation before release/promotion.
- Apply this methodology recursively to the harness itself. The trusted current release evaluates the candidate release against the harness codebase and external real-project/multi-turn/multi-agent/multi-model scenarios; the candidate cannot certify itself or change the evaluator, thresholds, evidence, or root of trust during evaluation.
