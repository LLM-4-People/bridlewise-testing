# Promotion

The promotion primitive (`harness promote`, development root alias `promote`): a
source branch carried to a target branch through a declared, versioned
profile — the target's tree is a projection of the source's, computed purely,
never a merge — and publishes it: one atomic push, never forced, then the
target's checkout fast-forwarded; a rerun is the resume, a rollback is a new
commit, and a reference-transaction hook promotes after every push of the
source. Generic: no branch name, path or command is spelled in code; a second
pair is a second profile file. The design is
`specs/merge-door-final.md` (the coordinator's notes); the guide is
[MERGE-GUIDE.md](../../../../docs/process/MERGE-GUIDE.md).

## What each file does

- `codes.ts` — the ONE table of the primitive's answers: each code's class (ok, input, precondition, errored, failed, integrity, parked), its exit code (`promotionExitCode`: an unattended run exits 0 for the answers that mean "not now") and its one remedy ([MERGE-GUIDE.md §7](../../../../docs/process/MERGE-GUIDE.md#7-codes) is held to it); `PromotionError`, the typed refusal every module raises; `mostSevereCode` (which refusal answers for a plan: integrity, input, failed, precondition, then errored); `answer` / `PromotionAnswer`, the envelope every verb answers with, and `answerWith` (an answer with facts added: the home's `promoterHome`, the chain's `chained`).
- `apply.ts` — `apply`, end to end, under the target ref's lock: the remote reconciled (`publication.ts`), the hold, the pending ref reconciled (a commit the remote already carries is published — finished, never rebuilt; one built for another S, or on an older T, dropped with its receipt; one the run's `--accept-target-edits` disagrees with, rebuilt), the plan's refusals but the two reasoned overrides, then `buildPromotion` (the tree landing — `../tree-landing.ts`: the candidate in the profile's promotion folder, settle, ONE commit with parents `[T, S]`, S's committer identity and date, the trailers —, the receipt blob `promotion-receipt/v1` with each command's evidence, the `pending` ref), then `publishCommit` and `finishPromotion`; a push rejected because the remote moved re-plans once. (The chain when the source moved meanwhile is the top-level entry's, `trigger.ts`, never the build's.) Every step is a checkpoint (`ApplyRun.checkpoint`, the crash test's seam) and every failure typed (`promotionErrorOf`). `buildAndPin` is the one build-and-pin path a rollback shares; `applyCeilingMs` derives the worst case of one apply (the lock wait, every command with its retries, a converge pass per generated output, the landing's git steps, the remote's timeouts).
- `promotion-run.ts` — what one run carries and shares: `ApplyRequest` (the overrides, `noPublish`, `noPush`, `auto`), `ApplyRun` (the git port, the runner, the generated and build outputs, the toolchain, `plan`, `checkpoint`), `promotionRefs` (`pending`, `hold`, `receipt`), the repository-scoped promotion folder (`promote-<repository id>/<profile>-<plan id>`), `withPromotionLock` (an unattended run never waits), `committerOf`, `promotionErrorOf`, `readReceipt`, `dropPending` (the pin dropped; its receipt too, unless the commit shipped — an ancestor of the target), `removeCandidate`, `targetTip`.
- `publication.ts` — the remote and the target's checkout: `reconcileRemote` in a `ReconcileMode` (a promotion's: the remote's source, target and hold fetched and judged — behind is fast-forwarded, ahead carried, apart `promotion_target_diverged` / `promotion_source_diverged`; a rollback's: the target and the hold only, the source never read or pushed; `noPublish`: read-only, nothing landed and no local hold deleted), the hold (`localHold`, `syncHold`, `holdBlob`, `setHold`, `pushHold`, `releaseHoldNow`), `publishCommit` (ONE `git push --atomic` of the commit, its receipt and a lagging source — never `+` —, `ls-remote` verification: the commit, or a tip that carries it, then the local landing: a fast-forward, a torn one completed, parking on overlapping edits, `promotion_target_index_locked`) and `finishPromotion` (the configuration's mode, the candidate's pinned build outputs installed as one journaled transaction, the index baseline, `depsStale`).
- `rollback.ts` — `rollback --to <promotion>`: a NEW commit restoring that promotion's tree (one parent, the tip; `Promotion-Restores`), built and published like a promotion, with the hold pushed in the same atomic push (its ref created only once R is pinned, again on a resume); `hold` and `release-hold`. A rollback of a rollback, the tip, or a commit off the profile's history is `promotion_rollback_invalid`.
- `trailers.ts` — the promotion trailers read back: `trailerHistory`, `promotionTrailersOf`, `profileOfTrailer` (which profile made the target's tip, how a checkout of the target finds its profile), `profileHistory`.
- `last-run.ts` — the per-profile last-run record (`promotion-last-run/v1` in the promotion area) and the log of each unattended run (`openUnattendedLog`: `unattended-<ms>-<pid>.log`, private, never truncating another; the record names its log, `HARNESS_PROMOTION_LOG`; a launch removes only the logs older than the record's start but the record's own): `lastRunRecorder` (the phase reached, the code it ended with, the duration), `readLastRun`, and `promotionState` (`idle`, `running:<phase>`, `interrupted:<phase>`, `held`, `parked`, `blocked`, `errored`, `failed`) the status and the exposure read.
- `trigger-hook.ts` — the text of `.githooks/reference-transaction` (`promotionTriggerHookText`), the one source the shipped hook, the commit guard and the installation checks compare against.
- `trigger.ts` — `promote auto --refs`: which profiles the moved refs trigger (`on-source-publish`, a source the refs name, never the promoter's own run), one unattended `apply --auto` started detached for each (a local hold is no reason: the run reads the remote's; its environment `unattendedEnvironment`: never the home's placement variable, its own log), the chain every top-level `apply` owes once it ended and its locks are released (`withUnattendedChain` / `chainUnattended`: the remote's source fetched; a tip the run's S does not contain goes through the trigger's rules; never after a hold or a coalesced run), and the ONE notice line for a profile whose last run did not end ok — `auto --text` is that line alone, what the hook prints on the pusher's stderr.
- `promote-arguments.ts` — THE GRAMMAR of `harness promote`: the verbs, `PromotionRequest`, `parsePromoteArguments` (argv → request, or the usage refusal: an override without a reason, or a reason without one) and `formatPromoteArguments` (request → argv, what the promoter home re-executes; `parse(format(request))` is the request). A leaf: the verbs and the command door both import it.
- `promoter-home.ts` — S's committed code promotes S: `promoterPlacement` (here when this engine's checkout is clean at S, when `HARNESS_PROMOTER_HOME` names it — `isPromoterHomeChild` —, or when the promoted repository does not host it — `engineCheckout`: git's answer that the engine is in no checkout, never a machine failure; otherwise the home) and `runInPromoterHome` (under the home's lock `promotion-home-<profile>`, which an unattended run never waits for: the detached worktree `<profile>-home` in the promotion folder moved to S, its config mode and the engine's own setup re-run when their inputs changed since the last source whose preparation PASSED — `promoter-home.json` in the profile's promotion area, written only after it passed; then the same request re-executed through the engine's CLI entry, `src/cli.ts harness promote … --source <S>`; a failed preparation is `promotion_home_setup_failed`/`_errored`, a child that answers no envelope `promotion_promoter_failed`/`_errored`).
- `profile.ts` — the profile: its strict, versioned schema (`bridlewise-promotion-profile/v4`), the rules a well-formed profile can still break (the JSON pointer of each: a path both included or derived and excluded, a spawn base that is not a folder prefix, …), the loader (`<promotion.profileDirectory>/*.json` of a tree) and the selector; `profileCommandNames` (the registry commands a profile runs).
- `projection.ts` — the projection: `classifyTree` (every path's one reason: derived, excluded, reached, included, companion, overlaid from the profile's overlay folder, or out by default; an overlay file of a kind the overlay does not declare (its allowlist; the profile refuses a kind of code), a link, one landing on an excluded path, or one naming a path the projection already carries is `promotion_overlay_invalid`; `shippedSources` is every shipped path with the source path its bytes come from; every shipped module is walked — the entry points AND the included modules — so the source's refusals cover all of them), `deriveManifests`, `projectSource` (the synchronous source side: the target's last promotion, the advisories, including `opaque_edge`), `planPromotion` (the derived lockfiles, the tree P written to the object store and verified, the never-rule, the target's direct edits with their patch, the deletion budget, `up_to_date` / `unchanged`, the plan id over every input: the commits, the profile blob, the registry commands it runs and the promoter's own code closure) and `explainPaths`.
- `transforms.ts` — the derived files: `deriveMakefile` (the kept rules of the source Makefile verbatim, `.PHONY` narrowed; a missing target, a dropped prerequisite, a kept recipe running make in this Makefile on a dropped target, or a line outside its grammar refused; pure), `deriveManifest` (the scripts list — a listed script the source lacks is refused —, pruned segments, the devDependencies the projection uses, the command word found behind `NAME=value` and `npx`/`npm exec`; pure) and `deriveLockfile` (the registry command in a per-call private scratch through the ONE runner, an errored run retried by the runner, memoized by its inputs and the toolchain's versions).
- `context.ts` — two levels: the REPOSITORY context (`resolveRepositoryContext`: the configuration, the repository and its configured git, the registry, the profiles any commit declares; `declaredProfiles`) and a PAIR's (`contextFor`: the profile READ FROM THE SOURCE COMMIT, S and T, `targetTip`); the verbs (`runPromotionVerb`: `status` (with the preflight, the pending and hold refs and the last run), `plan` — with the `source_evidence` advisories: the invoking checkout's judged runs of S against the last promoted source's, or `unmeasured` —, `explain`, `apply`, `rollback`, `hold`, `release-hold`, `auto`, each logged once; the ONE command runner built on first use) and `enginePromotionSource` (the exposure source the engine CLI installs: every signal answers one entry per declared profile).
- `forge-publish` (the verb: `promotionForgePublish` and `forgePublishWith` here; the publication is `../forge/publish/product.ts`) — on GitHub, the publisher App writes the product branch, from a checkout clean at S (`promotion_forge_not_at_source` otherwise). The verb drops any pending commit and builds the promotion itself (`applyPromotion --no-publish`, with the reasoned overrides passing through). It then checks the commit (`verifyBuiltProjection`): the profile and source trailers (`promotion_forge_profile_mismatch`), and a tree EQUAL to `recomputeProjection` (`apply.ts`: the plan's P settled by the profile's own phases in a fresh candidate). Any differing path is `promotion_forge_projection_mismatch`. Finally it carries the commit to the forge as a signed commit with parents `[T, S]`, refused when the branch moved since the build (`promotion_forge_target_moved`) or when the forge stored or signed something else (`promotion_forge_mismatch`), and writes the projection receipt the job attests.
- `verify` (the verb: `promotionVerify`, `verifyTarget` and `verifyProductCommit` here) — runbook P4.1's check of a product commit (default: the profile's target tip), which anyone holding the product and its source can run: it must be a promotion commit (`Projected-From`, `Promotion-Profile`), its profile must be the one this checkout declares at HEAD, that profile's source branch here must equal what its remote publishes now (`ls-remote` through the one git port; `promotion_verify_source_unconfirmed`; an unreachable remote is `promotion_verify_remote_unreachable`, never a fallback to the local copy), and its source must be on that branch's first-parent line, its landings, never a commit merged in from a side branch (which holds because the trunk ruleset allows merge landings only, pinned in settings-as-code: #486) (`promotion_verify_off_source`; trust never comes from the commit under check or from its source's own content), and its tree must EQUAL the projection recomputed from that source alone by the source's own promoter (the publisher's check, `verifyBuiltProjection`, naming each differing path). Away from a checkout clean at the source it re-runs in the promoter home. `promotion_verified` is the pass.
- `release-train.ts` — the product's release train (`planRelease`, github-only §9.4): event-driven, it departs when the product (the target of `promotion.release.profile`, read at HEAD) changed since the last release, the version its root `package.json` declares (the one version source until per-module versioning generates it, Q6, #101; parsed and ordered by the one semver owner, `src/extensions/semver.ts`) has no tag yet, at least one public record (a tracker item, read through `failure-owners.ts`) closed between the previous release's source and S (`no_record_closed`; `closedRecords`), `promotion.release.minIntervalHours` have passed since the newest release RECORD's own `published_at` (the forge's list, `--releases`; not read: the `releases_unread` reason) and the mode (`auto`, `manual`, `approval`) allows it; each unmet condition is a named reason of `promotion_release_not_due`. A product tip with no `Projected-From` is `promotion_release_source_unproven`; a version that is not semver or goes back is `promotion_release_version_invalid`. Only tags on the product's first-parent line are releases, and every one is annotated: a lightweight release tag there is `promotion_release_tag_lightweight` (integrity). No clock: `now` is an input.
- `release-notes.ts` — the release notes, generated from the records between the two releases' `main` sources: the landed pull requests (merge and `(#n)` subjects on the first-parent line), the tracker items closed (by type), the decision records added, changed or removed, and the names `Signed-off-by` / `Co-authored-by` credit (`creditedName`: the name before an address, a GitHub private address as its `@login`, never an address in any form); the first release names the prior releases' address. Pure: the same plan gives the same text.
- `release-assets.ts` — the one list of a release's assets and their names (`releaseAssetNames`: the source archive, the engine bundle, the guardian of the building platform, the SPDX SBOM, the pre-built documentation site, `SHA256SUMS`) and `assembleRelease` (every input required, else `promotion_release_assets_incomplete`; the source archive is `git archive` of the product commit; the checksums cover every asset).
- `release-cli.ts` — `harness release <records|plan|notes|assemble>`: the release train's door, answering this folder's envelope (`codes.ts`); `records` reads every release of the trunk through the forge as the publisher App (`listReleases`) and writes the records file the other verbs read (`--releases`), its one writer and reader; the clock is read here only (`--now` replaces it); `notes` and `assemble` build nothing for a train that waits.
- `promote-cli.ts` — the command door: reads argv through the grammar (`promote-arguments.ts`), answers the envelope (`../command-result.ts`, never the command table) with its `--text` report (the harness dispatch's one output option renders it), and maps the answer's class to the exit code; the verbs are `context.ts`'s.
