# publish

The publisher App's work on the forge (`app-registry.ts` names this folder as its owner): the product branch first, and later the releases, the projection, Pages and the ledger. Every request goes through the forge port (`../port.ts`, the one GitHub client), as the publisher App; nothing here retries or waits, so a budget or a failure reaches the caller as the forge's typed refusal.

## What each file does

- `git-data.ts` — the Git Data API on the port: `remakeCommit` carries one local commit to the forge. It uploads the blobs the commit changes against its first parent (each answered id checked), builds the tree on that parent's tree (the answered tree must be the local one), and makes the commit with no author, committer or signature, so GitHub signs it; an unsigned answer is refused. `branchHead` reads a branch, `advanceBranch` moves it only forward (`force: false`) after checking it still names the expected head, then re-reads it. `treeDelta` is the tree diff a re-made commit carries. Every mismatch is `forge_publication_mismatch` (integrity).
- `product.ts` — the product publication (decision PROMO-GH). `publishProduct` takes a promotion commit (its trailers must name its source and profile, and its parents must be [the product tip, the source]), refuses when the forge's product branch moved since the build, re-makes the commit with parents `[T, S]` and moves the branch. It answers the projection receipt (`bridlewise-product-projection/v1`): the published commit, the built commit, the tree, the source, the profile and the head it landed on. `forgePublishVerb` publishes a commit and writes the receipt's canonical bytes (`receiptBytes`) for the job to attest. `configuredProductForge` is the configured forge as the publisher App; it reads the installation token the job mints. The verb `harness promote forge-publish` (`promotion/context.ts`, `promotionForgePublish`) is what calls it: it BUILDS the promotion itself (any pending commit is dropped first, so nothing built elsewhere is ever carried), checks the built commit against the projection recomputed from S (`verifyBuiltProjection`: the profile and source trailers, and a tree equal to the plan's P but for generated outputs that differ only in their generated parts), and only then publishes.

## The publish job (in GH-2's generated `publish.yml`, environment `publish`, on every land; the generator lands with #67)

1. Check out `main` at the landed commit with `fetch-depth: 0`, fetch `product`, install both dependency trees, and set the config mode.
2. Mint the publisher App's installation token from the `publish` environment's `PUBLISHER_APP_KEY` and `PUBLISHER_APP_CLIENT_ID`, exported as `BRIDLEWISE_PUBLISHER_TOKEN`.
3. Build, check and publish: `harness promote forge-publish --source HEAD --out projection-receipt.json`. The first promotion onto the seeded product adds `--accept-target-edits <the plan's exact list> --allow-deletions --reason <text>`.
4. Attest `projection-receipt.json` (`actions/attest`, the receipt as the subject).
